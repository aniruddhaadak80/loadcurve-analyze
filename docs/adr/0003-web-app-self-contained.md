# ADR 0003 — The web app is self-contained, and says so when it is

- **Status:** Accepted
- **Date:** 2026-10-05

## Context

`apps/web` is the only part of this repository deployed to Vercel. Two facts constrain it:

1. **Vercel has no Python runtime.** The engine is a subprocess, so it cannot run there.
2. The rest of the repo is a multi-package monorepo built with turbo, so any workspace
   dependency from `apps/web` couples the deployment target to the local build order.

A deployed page that showed placeholder numbers would be worse than one that showed none.

## Decision

`apps/web` depends on **no workspace package at all** — only `next`, `react` and `zod`. It
imports no store, no plugin registry, no CLI code, and no engine client.

This is not tidiness. `vercel --prod` runs from `apps/web` **outside the npm workspace**, so a
workspace dependency is a 404 at install time. The first deploy attempt failed exactly that way:

```
npm error 404 Not Found - GET https://registry.npmjs.org/@loadcurveanalyze%2fengine-model
Error: Command "npm install" exited with 1
```

So `apps/web/lib/study.ts` is a hand-maintained **type mirror** of the engine's response shapes
rather than a re-export, and `getStudy()` always returns the **recorded result** from
`apps/web/lib/recorded-study.json` with `source: 'recorded'`. The page displays which it is
rendering.

The recorded file is generated by `scripts/record-study.mjs`, which runs the real engine. Two
tests keep it honest: one in `packages/engine-model` parses it against the real response schema,
and one in `packages/tools` asserts its digest matches a fresh engine run. The type mirror cannot
drift silently — if the engine changes shape, the schema test fails.

## Consequences

**Good**

- The Vercel build cannot break because a workspace build reordered or failed.
- `vercel --prod` works from a bare checkout of `apps/web`.
- The deployed bundle has a small, known dependency set.
- A deployed demo that shows a recorded run says so, in the page heading. No reader is misled
  about whether the numbers were computed for them.

**Bad**

- The deployed page's numbers are not live. That is the honest trade: a live number would require
  shipping Python to the edge, and a fake one would be a lie.
- Someone must remember to re-record after changing the example. This is enforced by a test, not
  by discipline — but a reviewer who changes `EXAMPLE_REQUEST` and does not re-record will see a
  failing test rather than a stale deploy.

**Rejected: shipping the engine to Vercel** via a WASM build or a hosted Python service. It would
make the demo live, at the cost of a second execution environment for the code whose determinism
is the product. The recorded result with a visible label is the smaller promise kept honestly.
